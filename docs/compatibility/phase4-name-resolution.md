# Phase 4: safe name resolution and create-if-missing references

Phase 4 extends the Phase 3 typed mutation protocol so a normal
`createTransaction` operation can identify a party, category, or subcategory by
human-readable name. Missing records can be created in the same atomic mutation
batch as the transaction.

## Protocol fields

The existing `createTransaction` operation accepts these additional optional
fields:

- `partyName`
- `categoryName`
- `subcategoryName`
- `createMissing`
- `categoryKind`

An ID and a name for the same reference are mutually exclusive. For example,
`partyId` and `partyName` cannot appear together.

`createMissing` defaults to `false`. A name that does not already exist is an
error unless the client explicitly sends `createMissing: true`. This prevents a
typing mistake from silently creating a permanent Grisbi record.

Example:

```json
{
  "type": "createTransaction",
  "accountId": "1",
  "date": "07/12/2026",
  "amount": "-24.90",
  "paymentMethodId": "1",
  "partyName": "Corner Shop",
  "categoryName": "Food",
  "subcategoryName": "Groceries",
  "createMissing": true
}
```

If none of those names exist, the server expands the single client operation
into `CreateParty`, `CreateCategory`, `CreateSubcategory`, and
`CreateTransaction`, then applies the complete expanded list once through the
Phase 2 mutation engine. Validation failure produces no file output and no
partial record creation.

## Name matching

Names are compared using a deterministic key:

1. Unicode NFKC normalization;
2. leading and trailing whitespace removal;
3. consecutive whitespace collapsed to one space;
4. Unicode case folding.

Accents are not removed. `Cafe` and `Café` remain distinct names.

A unique normalized match is reused. Multiple records with the same normalized
name are considered ambiguous and the mutation is rejected with the matching
record IDs. The client must then submit an explicit ID.

Subcategory names are resolved only within their parent category.

## Category direction

For a non-zero amount, category kind is derived from the amount:

- positive amount: `Kd=0`, credit category;
- negative amount: `Kd=1`, debit category.

A matching category of the wrong kind is rejected instead of creating a second
category with the same normalized name. Special categories (`Kd=2`) remain
reserved for transfer and split phases.

For a zero amount, an existing unique category can be reused. Creating a new
category for a zero amount requires `categoryKind` set to `0` or `1`.

## Batch behaviour

The planner simulates the same maximum-plus-one allocation rules used by the
mutation engine. Therefore:

- a party/category/subcategory explicitly created earlier in the batch can be
  referenced by name later in the same batch;
- repeated missing names are created once and reused by all later operations;
- the predicted IDs are verified naturally when the expanded batch is applied;
- a failure anywhere in the expanded batch leaves the original GSB bytes
  unchanged.

Protocol outcomes include:

- `operationIndex`: the original client operation index;
- `expandedOperationIndex`: the internal expanded operation index;
- `role`: `party`, `category`, `subcategory`, `transaction`, or `primary`;
- `autoCreated`: whether the record was generated by name resolution.

## Phase boundary

Phase 4 supports name resolution for normal transaction creation. Existing
low-level create operations remain available. Transaction updates continue to
use explicit Grisbi IDs, and the Vue editor is not migrated in this phase.
Reliable frontend CRUD integration belongs to Phase 5. Transfers and split
transactions remain protected for their dedicated phases.
